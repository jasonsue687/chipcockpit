0. 低分步骤的共性药方

从 Step 2 / 3 / 5 / 10 这几个评分较低步骤的解法回看，根因和解法可以归纳成 4 条通用模式：

低分根因 共性解法 典型应用
AI 看不到的隐性约束
(package / 工艺经验 / 上代芯片)		 显式化成 YAML 握手文件，把隐性变显性 Step 2 约束前置 · Step 3 协同握手文件 · Step 4 PG 模板
决策不可逆 / 拍板代价大 多候选 + 数据对比，让人在数据上选而非直觉上选 Step 2 多档探针 · Step 5 多候选 + Pareto
容易陷入局部最优 / 主观偏见 / Anchoring AI 当质检员 / 评审员，而非决策者 Step 3 Lint · Step 5 Critique-Only · Step 10 A/B 归因 · Step 10 逃逸提案
项目特定 know-how 会随人员流动丢失 沉淀成可检索的语料 / 规则 / 模式库 Step 5 案例模式库 · Step 10 启发式库 · Step 7 hierarchy 命名规则
通用心法：碰到任何 AI 评分低的步骤，先问"是哪一条根因？"，再套对应解法。不要在 AI 不擅长的维度上硬刚，找到它真正擅长的角色。

1. 用评分划分"自治度"分层

  • 评分 8–10 的步骤 → Agent 可主动生成 TCL 脚本 → 执行 → 给出 summary，人只做事后审核 / 一次性参数确认。
  • 评分 6–7 的步骤 → Agent 应"先生成多个候选方案 + 风险对比"，让用户在 UI 中选择，再落 TCL。
  • 评分 ≤5 的步骤（尤其 macro placement、IO 排列） → Agent 角色变成信息提供者：fanin/fanout 矩阵、flyline 图、congestion 预估，由人 drag-and-drop，Agent 只负责"语义化记录决策原因"。

2. 人在回环的"检查点"要明确

根据上面的评分，4 个强制人工检查点是少不了的：

  • ✅ Spec 确认（开始前）：工艺角、面积目标、power budget
  • ✅ Die / Core 尺寸拍板（Step 2 后）
  • ✅ Macro Placement Review（Step 5 后，可能多轮）
  • ✅ Sign-off QoR Review（Step 9–10 后，决定是否进 placement）

其他步骤可走"默认执行 + 异常打断"模式（PreToolUse hook 拦危险命令即可）。

3. Agent 的工具链应该长这样

  • 读：LEF/Lib/SDC/Netlist 解析 · 报告解析（congestion / IR / timing）· 项目目录 grep
  • 写：TCL 脚本生成 · 决策日志 (jsonl) · YAML spec 落盘
  • 执行：Innovus（建议无头模式 + log 流式回看，避免一把跑完丢上下文）
  • 不要做：静默修改 floorplan.def · 自动 git push · 删除 run 目录

4. 文件系统握手 (Filesystem Handoff) 比聊天可靠

Macro 放置、PG 模板、halo 规则这些"工程师手感"，写成 YAML / DEF 落盘后，下一次 session 进来 Agent 仍能 100% 复现。聊天里的"上次咱们把 SRAM 放左下角"是会丢的。

5. 一个值得借鉴的失败模式 (Anti-pattern)

不要让 Agent 在 macro placement 步骤"独立想出一个 placement 然后让用户改"—— 心理学上这叫 anchoring，用户会下意识在 AI 的 placement 上小修小补，错过本来更优的全局解。 正确做法：先给 connectivity heatmap + dataflow 推荐方向，让用户先画第一稿，Agent 再做 critique。

6. 评分会随项目变化

评分是对"通用 floorplan 流程"的判断。对特定项目，如果已经有成熟的 PG 模板 / 上代芯片的 floorplan 可参考， 很多 5–7 分的步骤会跃升到 8+；反之，全新工艺 / 新架构第一次 tape-out 时，原本 7 分的 PG planning 也可能跌到 5。 建议 Agent 维护一个 project_maturity.yaml，动态调整自治度。
