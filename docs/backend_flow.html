chip-backend-ai · 后端设计开发流程

自治编排器 + 文件系统交接协议 + 人类审批 Spec 的三层架构 · 基于 docs/workflow.md Master Plan V3 整理 · 当前阶段 Agent 处于 Simulation Mode（EDA 工具未接入）

系统总览

系统的核心思想是：抽象目标具象化 → 人类审批 → 编排器按规矩统筹 → 智能体干活并落盘。 没有写死的线性流水线，而是依靠一个高自治的编排器 (Orchestrator) 读盘思考、按需路由 Sub-agent， 所有跨 Agent 通讯一律走文件系统。

单一决策中枢

Orchestrator

由 run-chip-flow skill 驱动。读状态机 → 决策 → 唤醒 Sub-agent → 处理评估结果。 所有跨阶段归因（"floorplan 的 macro 摆放是否导致 routing congestion"）都由它判定。

人在回路

Spec_Agent

独立于编排器的意图层 Agent。负责把模糊目标翻译成结构化 YAML Spec，落盘前必须经过人类审批。 运行中遇到不可达约束，编排器会重新唤醒它做 spec 修订。

领域执行单元

Domain Agents

Floorplan / CTS / Route / Timing ECO。统一生命周期：唤醒→读盘→执行→自评估→落盘→休眠。 当前 EDA 工具尚未接入，所有执行通过 stage_simulator.py 模拟产出 pass/fail。

设计原则

原则含义
单一决策中枢只有编排器读状态机并决定下一步，Sub-agent 不主动决策
万物皆落盘禁止 Agent 之间内存传参，全部数据走 workspace 文件系统
Spec 必须人审初始生成和后续修订，落盘生效前都要人类 Approve
Append-only 审计旧 run 目录、旧 spec 版本永不删除，decisions.jsonl 只增不改
评估含原始数值eval_result.yaml 每项指标都要带 target 和 actual，便于 Spec 变更后重判

顶层运行时闭环

0. 环境准备识别/录入 Innovus 路径
1. 工作区初始化创建 .chipflow 目录结构
2. Spec 生成Spec_Agent 翻译模糊目标
3. 人类审批Approve / Reject
4. 编排器思考读盘 → 选 Agent
5. Sub-agent 执行读 Spec → 跑 → 自评估
6. 落盘交接_meta + eval_result + artifacts
7. 再编排retry / rollback / next / revise / done
当前状态：所有领域 Agent 还没有接 Innovus/Genus，执行步全部走 core/workflow/stage_simulator.py， 会读 stage spec 随机生成处于 pass 区间的 actual 值，并在 eval_result.yaml 中打上 simulated: true。 编排器的状态机、retry/rollback/revise_spec 路径都可以端到端跑通，只是 PPA 数据是合成的。

Phase 0 · 环境准备

插件在任意机器上运行，EDA 工具（当前是 Innovus）路径机器之间各不相同。 所以在任何项目首次使用之前，run-chip-flow 会先做一次环境识别，把 Innovus 的可执行文件路径固化进 JSON。后续所有需要调 EDA 的阶段都从这份 JSON 读路径。

存储位置

默认

机器级 · ~/.chip-backend-ai/env.json

Innovus 路径绑定到机器，不绑定到项目 —— 一次检测，全机器所有项目复用。 升级/迁移 Innovus 之后会被 check 命令识别为 stale 并触发重新识别。

可选

项目级 · <workspace>/env.json

当一个项目必须钉死特定的 Innovus 版本时，所有 env_manager 子命令都接受 --config <path> 来指定一份项目内的配置，覆盖默认机器级配置。

JSON Schema

{
  "version": "1",
  "detected_at": "2026-05-17T10:30:00+00:00",
  "eda_tools": {
    "innovus": {
      "binary": "/opt/cadence/INNOVUS221/bin/innovus",
      "install_dir": "/opt/cadence/INNOVUS221",
      "version": "221",
      "source": "PATH"          // PATH | env:<VAR> | glob:<pattern> | user-provided
    }
    // 未来加 genus / tempus / quantus 直接挂在 eda_tools 下
  }
}

编排器的 Phase 0 流程

1. checkenv.json + binary 是否健康
2. detect --save缺失则自动识别并落盘
3. 问人自动识别失败 → 让用户提供路径
4. set验证可执行性 → 写入 JSON
5. → Phase A进入工作区初始化

Sub-agent 使用方式

领域 Agent 在真实调用 Innovus 时，从 env_manager 读取路径而不是写死：

from plugins.chip-backend-ai.core.env.env_manager import get_tool_binary

innovus = get_tool_binary("innovus")
if innovus is None:
    raise RuntimeError("Innovus not configured — orchestrator should have caught this in Phase 0")

subprocess.run([innovus, "-files", "run.tcl", "-nowin"], check=True)
当前 Simulation 模式：所有领域 Agent 走的是 stage_simulator.py， 暂不需要真实 Innovus。但 Phase 0 仍会执行 —— 一是为未来 EDA 接入预热配置； 二是没有有效路径时立刻暴露问题，避免到真实集成时才发现机器配置不对。

Workspace 目录结构

每次启动新任务，workspace.py init 会在当前目录下创建一个隔离的 .chipflow (或 .chipflow_2, ...)。所有 Spec、状态、run 记录都在这个目录里。

workspace/ ├── spec/ # 全部 Spec 文件（含历史） │ ├── global_spec.yaml # 当前生效的全局 Spec │ ├── stages/ │ │ ├── floorplan.yaml # floorplan 阶段 Spec │ │ ├── cts.yaml # CTS 阶段 Spec │ │ └── route.yaml # route 阶段 Spec │ └── history/ # 旧版本归档（只增不删） │ ├── global_spec_v1.yaml │ └── global_spec_v2.yaml │ ├── state/ # 编排器读写 │ ├── machine.yaml # 全局状态机快照 │ └── decisions.jsonl # 编排器决策日志（append-only） │ ├── stages/ # Sub-agent 落盘区 │ ├── floorplan/ │ │ ├── run_001/ │ │ │ ├── _meta.yaml # 元数据（谁/何时/spec_version） │ │ │ ├── eval_result.yaml # 自评估结果 │ │ │ ├── artifacts/ # Tcl、约束文件等 │ │ │ └── reports/ # EDA 工具原始 report │ │ └── run_002/ # 重试递增 run_id │ ├── cts/run_001/ │ └── route/run_001/ │ └── checkpoints/ # DEF/DB 快照（回滚恢复点） ├── post_floorplan_run001.def └── post_cts_run001.def

三类核心文件

Spec

spec/

Spec_Agent 产出，落盘前需人审。主文件可变，但旧版本会归档进 history/， 每次修订 spec_version 递增。Sub-agent 的 _meta.yaml 会记录运行时依据的版本。

State

state/

machine.yaml 是状态机快照，原子覆写；decisions.jsonl 是只增不改的决策审计链。 编排器每次决策都会同时更新这两个文件。

Stages / Checkpoints

stages/ + checkpoints/

每次 Sub-agent 执行产生一个 run_NNN/。同一阶段重试不覆写，递增 run_id。 checkpoints 存的是 DEF/DB 快照，用于跨阶段 rollback 时把上游恢复到某次成功的状态。

Agent 矩阵

系统目前定义了 5 个 Sub-agent，按职责分两类。所有 Agent 都遵循统一生命周期，由编排器通过 Agent 工具唤醒。

意图层

Spec

spec-agent

职责：把模糊人类目标翻译为结构化 YAML Spec（global + stages）。

唤醒场景：

  • initial — 第一次从模糊目标生成 Spec
  • revision — 编排器判定 Spec 不可达，提出修订建议
  • adjustment — 人类主动要求改

关键约束：输出必须经人审才能生效。

领域执行层 Simulation Mode

Stage 1

floorplan-agent

职责：宏单元摆放、电源网络规划，输出初始物理布局。

典型指标：utilization、congestion_hotspot、macro_channel_width_um

当前模式：通过 stage_simulator.py --stage floorplan 合成 eval 结果。

Stage 2

cts-agent

职责：时钟树综合、skew 平衡、buffer 插入。

典型指标：clock_skew_ps、clock_latency_ps、buffer_count

上游依赖：读 post_floorplan checkpoint。

Stage 3

route-agent

职责：全局 + 详细绕线、拥塞解决、DRC 修复。

典型指标：drc_violations、routing_overflow、wns_ns

上游依赖：读 post_cts checkpoint。

On-demand

timing-eco-agent

职责：setup/hold 局部修复、DRC 增量修复。

调度方式：不在常规序列里，编排器在某阶段反复失败、但根因是局部时序时按需唤醒。

spec：spec/stages/timing_eco.yaml 可选；缺失时 simulator 输出最小通过结果。

统一生命周期

唤醒编排器通过 Agent 工具传入 workspace+run_dir
读盘读 stage spec + 上游 eval / checkpoint
执行调 EDA（当前：simulator）
自评估提取指标 → 比对阈值
落盘_meta + eval_result + artifacts
休眠控制权回编排器
评估两条铁律： ① eval_result.yaml 每项指标必须同时记录 target 和 actual，不能只输出 pass/fail。 ② 跨阶段归因（"floorplan 摆放导致 routing congestion"）不由 Sub-agent 做，归编排器。

端到端执行示例

展开下面的折叠块，一步步看一次完整的 flow 从启动到完成都发生了什么。

⓪ Phase 0 · 环境准备（机器级，一次性）

识别本机 Innovus 路径并固化到 ~/.chip-backend-ai/env.json。详细机制见 环境准备 页签。

# 1. 看下当前是否已有有效配置
python3 ${CLAUDE_PLUGIN_ROOT}/core/env/env_manager.py check --tool innovus
#   → exit 0 直接跳到 Phase A
#   → exit 1/2 进入下一步

# 2. 自动识别
python3 ${CLAUDE_PLUGIN_ROOT}/core/env/env_manager.py detect --save

# 3. 自动识别失败 → 编排器问用户：
#   "未在本机找到 Innovus，请提供绝对路径"
python3 ${CLAUDE_PLUGIN_ROOT}/core/env/env_manager.py \
  set --tool innovus --path /opt/cadence/INNOVUS221

Resume 行为：每次再次调用 skill 都会重跑 Phase 0 的 check，因为 Innovus 可能被升级、卸载或挪位置。

① Phase A · 工作区启动

用户没有现成 workspace 时，run-chip-flow skill 默认在当前目录创建一个隐藏的 .chipflow。

python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py init
# → 输出 JSON：{"workspace": ".../.chipflow"}

之后所有命令都用这个路径作为 --workspace 参数。状态机初始化为 INIT。

② Phase B · Spec 生成 + 人审

询问用户模糊目标（例："跑通这个 block 的 route，主要看有没有大的 congestion，时序稍微超一点没关系"）， 然后转移状态并唤醒 Spec_Agent：

state_manager.py transition --event human_input
decision_logger.py log --action dispatch --target spec_agent

Agent({
  subagent_type: "chip-backend-ai:spec-agent:Spec Agent",
  prompt: "Workspace: ...\nScenario: initial\nHuman Goal: ..."
})

Spec_Agent 完成 → 状态进入 SPEC_REVIEW。Orchestrator 把 global_spec.yaml 与各阶段 spec 展示给人审。Approve → 进入 SCHEDULING。Reject → 回 SPEC_DRAFTING 以 scenario: adjustment 重唤醒 Spec_Agent。

③ Phase C+D · 调度循环 + 阶段派发

SCHEDULING 是一个不动点循环。每轮：

1. state_manager.py read           # 读 machine.yaml
2. state_manager.py check-budget   # 检查总预算
3. 读上一次 eval_result.yaml
4. 应用决策逻辑（见"编排器决策"页签）
5. decision_logger.py log
6. 执行：dispatch / retry / rollback / revise_spec / complete / abort

派发某个领域 Agent 时：

workspace.py create-run --stage floorplan
state_manager.py transition --event dispatch
state_manager.py update-stage --stage floorplan --status running --run-id run_001

Agent({
  subagent_type: "chip-backend-ai:floorplan-agent:Floorplan Agent",
  prompt: "Workspace: ...\nRun directory: stages/floorplan/run_001/\n
           Spec version: v1\nStage spec: spec/stages/floorplan.yaml"
})

Agent 返回后读 eval_result.yaml，更新 stage 状态，agent_done 转回 SCHEDULING。

④ Phase E · Spec 修订（可选支路）

某阶段反复失败、且根因像是 Spec 太严：

state_manager.py transition --event revise_spec
decision_logger.py log --action revise_spec --reason "floorplan 连续 3 次 congestion 超阈值"

Agent({
  subagent_type: "chip-backend-ai:spec-agent:Spec Agent",
  prompt: "Scenario: revision\nContext: <失败的 eval_result 数据>"
})

Spec_Agent 给出新版本 → 再走一遍人审 → spec_version 递增 → 回到 SCHEDULING。 编排器据此重新判定已通过阶段的结果是否需要重判。

⑤ Phase F · 完成 / 中止

COMPLETED：读各阶段 eval_result 汇总最终 PPA，告诉用户成品在哪。

ABORTED：报告失败阶段、预算消耗、最后一次 eval 数据，并给出可能的人工干预建议。

两种终态都不会自动清理 workspace，便于事后审计。

⑥ Resume · 中断恢复

再次调用 skill 时，先读 state/machine.yaml 的 current_state，从对应 Phase 恢复：

INIT          → 进入 Phase B
SPEC_DRAFTING → 检查 spec 文件，若已存在则转 SPEC_REVIEW
SPEC_REVIEW   → 重新展示 spec 让人审
SCHEDULING    → 进入调度循环
STAGE_RUNNING → 看 eval_result 是否已落盘，是则 agent_done
COMPLETED/ABORTED → 直接报告最终状态

编排器决策逻辑

SCHEDULING 是中枢状态。每次进入 SCHEDULING，编排器都会执行以下决策树：

读取 state/machine.yaml
读取最近一次 run 的 eval_result.yaml

IF 全部阶段尚未跑过（all pending）:
    → dispatch 第一个阶段 (floorplan)

IF eval_result.overall == "pass":
    IF 所有阶段都已通过 + 满足终止条件:
        → all_passed → COMPLETED
    ELSE:
        → dispatch 下一个 pending 阶段

IF eval_result.overall == "fail":
    IF 该阶段 retry_count < max_stage_retries:
        → 同阶段 retry（递增 run_id）
    ELIF eval_result.recommendation == "rollback":
        → dispatch 更早阶段，parent_run 指向当前 run
    ELIF 全局预算耗尽:
        → budget_exhausted → ABORTED
    ELSE:
        → revise_spec（Spec 可能过严）

IF eval_result.overall == "partial":
    读 metrics 明细
    IF 失败的指标不阻塞下一阶段:
        → 带着 partial 推进
    ELSE:
        → 按 fail 逻辑处理

决策类型对照

action目标状态典型理由
dispatchSTAGE_RUNNING正常推进下一阶段或同阶段重试
retrySTAGE_RUNNING本阶段失败，重试次数未达上限
rollbackSTAGE_RUNNING (更早阶段)下游失败但根因在上游
revise_specSPEC_DRAFTING反复失败、Spec 可能过严
all_passedCOMPLETED满足 termination_criteria
budget_exhaustedABORTED全局重试预算耗尽

跨阶段 Rollback 协议

  1. 编排器识别下游失败的根因是某个上游阶段（例如 routing congestion → floorplan macro 摆放）
  2. 从 checkpoints/ 加载该上游阶段的某次成功 checkpoint
  3. 在该上游阶段创建新 run，_meta.yaml 里的 parent_run 指向触发回滚的下游 run
  4. 全局重试预算 -1
  5. 被回滚阶段的旧 run 目录全部保留，便于审计

失败注入测试（Simulation 配套）

用法：用户对编排器说"让 CTS 第一次失败"或"让 floorplan 第一次失败并建议回滚"。 编排器维护一个 fail_plan，在派发对应 run 时把 Simulate fail: true / Fail metrics: ... / Recommendation: ... 追加到 Agent prompt，stage_simulator 会按提示产生 fail 结果。 用于在没有真实 EDA 工具的情况下端到端测试 retry / rollback / revise_spec / abort 路径。

文件系统交接协议

所有 Agent 之间、Agent 与编排器之间的通讯都通过 workspace 下的 YAML / JSONL 文件。schema 由 templates/ 下的四份模板锁定，编排器和 Sub-agent 都不应擅自加字段。

① _meta.yaml  编排器识别 run 的唯一入口

agent: floorplan_agent
stage: floorplan
run_id: run_001
timestamp: "2026-04-12T14:30:00Z"
spec_version: v2                # 基于哪个版本的 Spec 执行
parent_run: null                # 回滚后重跑时指向触发回滚的 run
status: completed               # running | completed | failed
checkpoint: "checkpoints/post_floorplan_run001.def"

② eval_result.yaml  编排器决策依据

stage: floorplan
run_id: run_001
spec_version: v2
overall: pass                   # pass | fail | partial

metrics:
  - name: utilization
    target: { min: 0.65, max: 0.75 }
    actual: 0.71
    status: pass
  - name: congestion_hotspot
    target: { max: 0.85 }
    actual: 0.72
    status: pass

recommendation: proceed         # proceed | retry | rollback | escalate
retry_context: null             # recommendation=retry 时说明要调什么参数
escalation_reason: null         # recommendation=escalate 时填原因

③ machine.yaml  状态机快照（原子覆写）

current_state: SCHEDULING
spec_version: v2
global_retry_budget: { max: 15, used: 4 }

stages:
  floorplan:
    status: passed              # pending | running | passed | failed
    current_run: run_002
    retry_count: 1

文件生命周期规则

场景处理方式
同阶段重试旧 run_NNN/ 不动，创建新 run，run_id 递增
跨阶段回滚被回滚阶段旧 run 保留；新 run 的 parent_run 指向触发回滚的下游 run
Spec 变更旧 spec 移入 spec/history/，主文件覆写，spec_version 递增
任务终止整个 workspace 不自动清理，便于审计

常用 CLI 命令

所有命令都不需要包管理器，直接用 python3 跑。${CLAUDE_PLUGIN_ROOT} 即 plugins/chip-backend-ai/。

Workspace

# 自动创建 .chipflow（已存在则递增后缀）
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py init

# 自定义位置 / 名称
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py init \
  --path <parent_dir> --name <custom_name>

# 为某个阶段创建新 run 目录（自动递增 run_NNN）
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py create-run \
  --workspace <ws> --stage floorplan

State Machine

# 读状态机快照（JSON 输出）
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py read --workspace <ws>

# 触发状态转移（事件必须在 TRANSITIONS 表中）
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py transition \
  --workspace <ws> --event human_input --detail "User provided goal"

# 更新某阶段状态
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py update-stage \
  --workspace <ws> --stage floorplan \
  --status passed --run-id run_001 \
  --eval-path "stages/floorplan/run_001/eval_result.yaml"

# 设置 spec 版本
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py \
  set-spec-version --workspace <ws> --version v1

# 检查全局重试预算
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py \
  check-budget --workspace <ws>

Decision Logger

# 追加一条决策
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/decision_logger.py log \
  --workspace <ws> \
  --from-state SCHEDULING --to-state STAGE_RUNNING \
  --action dispatch --target floorplan_agent --run-id run_001 \
  --reason "Initial floorplan"

# 读最近 N 条决策
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/decision_logger.py read \
  --workspace <ws> --last-n 5

Spec Manager

# 读当前 spec
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/spec_manager.py read --workspace <ws>

Stage Simulator（当前模拟执行入口）

# 普通通过
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/stage_simulator.py \
  --workspace <ws> --stage floorplan \
  --run-dir <run_dir> --spec-version v1

# 注入失败（端到端测试编排器 retry/rollback/revise）
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/stage_simulator.py \
  --workspace <ws> --stage cts \
  --run-dir <run_dir> --spec-version v1 \
  --force-fail \
  --fail-metric clock_skew_ps \
  --recommendation rollback \
  --escalation-reason "skew 无法在本阶段收敛"
