🚀 项目介绍

chip-backend-ai 是一个 Claude Code 插件，目标是给芯片物理设计（后端） 工程师提供一个智能助理：既能查 EDA 文档、又能自主驱动后端流程。

📚知识子系统
一个渐进式披露的知识库，覆盖 Cadence Innovus 等 EDA 工具。包含 6 个 Skill： 浏览专家文档、按层级导航 User Guide、查 Tcl 命令、解释 EDA 概念、PDF 转 Markdown。
🤖编排子系统
一套自治的后端流程引擎。状态机驱动 + 子 Agent 分工（Spec、Floorplan、CTS、Route、 Timing ECO），人在关键节点介入审批，文件系统作为 handoff 协议。
💡 推荐阅读顺序
README.md → 本指南 → CLAUDE.md → proposals/workflow.md（深入编排器设计时再看）。

🎯 两个核心概念：插件开发 vs 项目开发

这是新人最容易混淆的一点。请先把这两件事在脑子里分清楚：

🔧① 插件开发

开发对象：Claude Code 的 plugin 本身（即本仓库）。

你在改：Skill、Agent、router、knowledge base、workflow 编排逻辑。

目的：让这个 AI 助理更强、更准。

谁来做：插件团队 / Plugin maintainer。

🏗️② 项目开发

开发对象：一个具体的芯片设计项目。

你在用：本插件提供的 Skill / Agent / Workflow 来跑后端流程。

目的：把某颗 SoC / IP 的物理设计跑通。

谁来做：后端设计工程师 / 使用者。

① 插件开发是怎么回事？

Claude Code 的 plugin 通过清单文件 + 自动发现机制注册功能。本仓库内的开发对象包括：

  • Skill（skills/*/SKILL.md）：渐进式披露的能力单元。例如「查 Innovus 命令」就是一个 Skill。
  • Agent（agents/*/AGENT.md）：可被编排器调度的子智能体。例如 floorplan-agent。
  • Workflow（core/workflow/）：状态机驱动的多阶段编排核心。
  • Knowledge base（knowledge/）：专家文档 + PDF 转换后的层级化知识。
📌 修改插件代码后
在 Claude Code 中重新加载插件（/plugin 或重启），即可生效。

② 项目开发是怎么回事？

当你使用这个插件去跑一颗芯片时，你的工作目录通常是另一个 repo（你的芯片设计 repo）。 在那里，你会：

  • 调用 /run-chip-flow 启动后端流程；
  • 让 spec-agent 把你的设计需求转成 YAML spec；
  • 让 floorplan / cts / route agent 接力执行；
  • 在 workspace/ 目录看到完整 handoff 文件 + 决策日志。
🎓 类比理解
把插件开发想象成「造一台数控机床」，把项目开发想象成「用这台机床去加工零件」。 本指南后面讲的 Git 协作流程，主要面向插件开发者——也就是你。

🔗 桥梁：你写的 plugin 是如何被项目开发用上的？

新人最常问的问题：「我改了 plugins/chip-backend-ai/ 里的代码，跑芯片项目的人怎么就能用上？」
答案是——通过 Claude Code 的 plugin 注册机制把本地仓库目录挂载进去。

📁 本地仓库
/path/to/chipcockpit
→
🔌 Claude Code
注册为 plugin
→
🏗️ 项目开发会话
/run-chip-flow ...

本地仓库的任何改动 → Claude Code 立即看到 → 项目会话里可以用最新版本

关键事实

  • Claude Code 并不会去 GitHub 上拉 plugin，它直接读你本地磁盘上的某个目录。
  • 这个目录就是 plugins/chip-backend-ai/（plugin 根，里面有 .claude-plugin/plugin.json）。
  • 你修改 → 保存 → reload，新行为立刻在「项目开发」会话里生效，不需要发版、不需要 pip install。
  • 因此「插件开发」和「项目开发」其实可以在同一台机器、两个 Claude Code 窗口里并行：一个窗口改 plugin，另一个窗口跑芯片。

怎么挂载？（先有个印象，第 4 节会再操作一次）

在 Claude Code 的会话窗口里，直接对 AI 说：

👤 你 帮我把本地这个目录注册成 plugin：
/path/to/chipcockpit/plugins/chip-backend-ai/
🤖 Claude Code 好的，使用 /plugin 命令把它登记为本地 plugin … 已注册 ✓
现在你可以使用 /run-chip-flow、/list-expert-topics 等 6 个 Skill。
📌 一句话总结
本地 git 仓库目录 ≡ 你本地的 plugin 源码。Claude Code 通过路径注册「指向」它， 你改它就是改 plugin，你的同事 clone 后挂载自己的本地目录，就拥有了一份独立、可独立修改的 plugin。

🛠️ 环境准备

  1. 安装 Git 与 Python 3

    macOS 通常自带；Linux 用包管理器；Windows 推荐 Git for Windows + Python.org 官方安装包。

    git --version       # 应 ≥ 2.30
python3 --version   # 应 ≥ 3.9

  2. 配置 Git 身份

    第一次使用需要告诉 Git 你是谁。请用真实姓名和公司邮箱，commit 历史里都会出现。

    git config --global user.name "Your Name"
git config --global user.email "you@company.com"
git config --global init.defaultBranch main
git config --global pull.rebase false   # merge 模式（推荐新人）

  3. 配置 GitHub 认证（SSH 推荐）

    生成 SSH key 后，把公钥贴到 GitHub → Settings → SSH and GPG keys。

    ssh-keygen -t ed25519 -C "you@company.com"
cat ~/.ssh/id_ed25519.pub   # 复制输出，粘到 GitHub
ssh -T git@github.com         # 测试连通

  4. 安装 Claude Code

    参考官方文档 claude.com/claude-code。 安装好后再把本地的 chip-backend-ai 仓库注册为 plugin。

  5. 创建你的工作目录

    团队约定所有人的本地仓库都放在 /path/to/projects/ 下， 再按自己的用户名建一个子目录（例如 dev-a、dev-b）。

    # 把下面的 dev-a 换成你自己的用户名
mkdir -p /path/to
cd /path/to

    为什么要统一路径？这样 PSR 工具、CI 脚本、log 路径都能套用同一套模板，遇事互相帮忙时一眼能知道对方在哪儿。

🌳 Git 多人协作流程

本仓库托管在 GitHub， 采用「Fork-less Feature Branch + Pull Request」工作流。 每个人在自己本地克隆一份仓库，开独立分支开发，完成后推送并发起 PR。

📊 协作示意图

每位开发者持有独立的本地仓库，各自的 Claude Code plugin 指向自己的本地路径； 通过独立分支 + PR 收敛到远端 main。
🔑 三个关键认知
  1. 每个人都有完整的本地仓库（不是只下载某几个文件）。
  2. main 分支永远只通过 PR 合并，禁止直接 push。
  3. 分支命名要能一眼看出谁在做什么：feat/dev-a-cts-skew、fix/dev-b-router-typo。

1️⃣ 克隆代码仓库

团队约定所有人的本地仓库都放在 /path/to/<your-username>/ 下。 下面以用户 dev-a 为例（你换成自己的就好）。 

# 1) 进到自己的用户目录（没有就先 mkdir -p）
cd /path/to

# 2) clone（仓库会落在 ./chip-backend-ai/）
git clone git@github.com:jasonsue687/chip-backend-ai.git
cd chip-backend-ai

# 3) 确认 origin 指向 GitHub
git remote -v
cd /path/to
git clone https://github.com/jasonsue687/chip-backend-ai.git
cd chip-backend-ai

克隆完成后，本地完整路径是：

/path/to/chipcockpit/

记住这个路径——下一步把它告诉 Claude Code。

👥 每个人一份独立目录
团队里 5 个人就有 5 个独立的本地仓库：.../dev-a/、.../dev-b/、.../dev-c/ … 互不影响。

2️⃣ 让 Claude Code 指向你的本地 plugin

这一步把刚才那个本地目录注册到 Claude Code 里，于是：

  • 你本地的改动（Skill、Agent、router、workflow…）会被 Claude Code 立即读取；
  • 之后在项目开发会话里使用 /run-chip-flow 等命令，跑的就是你最新版本；
  • 这条链路就是「插件开发」和「项目开发」的实际连接点。

方式 A：让 Claude Code 帮你接入

打开 Claude Code 会话窗口，直接说：

👤 你（dev-a） 我刚把 chip-backend-ai 仓库 clone 到本地了，路径是
/path/to/chipcockpit/plugins/chip-backend-ai/
帮我把它注册成 plugin，并确认能用。
🤖 Claude Code 好的，我用 /plugin 命令把这个本地路径登记一下，然后列出你能调用的 Skill / Agent。
✅ 注册成功。现在你可以使用：
/run-chip-flow · /list-expert-topics · /read-expert-doc · /search-eda-command · /read-eda-concept · /pdf-to-markdown

方式 B：自己用 /plugin 命令

在 Claude Code 输入框敲：

/plugin   # 然后按提示选择「本地路径」并填入下面这个路径
/path/to/chipcockpit/plugins/chip-backend-ai/
⚠️ 注意路径必须到 plugins/chip-backend-ai/ 这一层
因为这一层目录下才有 .claude-plugin/plugin.json，那是 Claude Code 识别 plugin 的入口。 填到外层 git 仓库根目录是识别不出来的。

验证

在 Claude Code 里随便输入 /，看下拉里有没有 run-chip-flow 等 Skill。 有就说明挂载成功；如果改了代码没生效，回会话里说「reload 一下 plugin」即可。

🔄 改完 plugin 代码后
大多数 Skill / Agent 的 Markdown 改动是即时生效的。如果改了 Python 代码或者 plugin.json， 让 Claude Code 帮你 reload：「帮我 reload 一下 chip-backend-ai plugin」。

3️⃣ 创建你的开发分支

每个新任务都开一个新分支。不要在 main 上直接改代码。 你可以让 AI 帮你做，也可以自己跑命令。

👤 你（dev-a） 帮我从最新的 main 拉一个分支 feat/dev-a-cts-skew 出来。
🤖 Claude Code 好的，先同步 main，再开新分支： 
$ git checkout main
$ git pull origin main
$ git checkout -b feat/dev-a-cts-skew
✅ 已切到 feat/dev-a-cts-skew，可以开始改代码了。
想自己敲命令？点开看 
git checkout main
git pull origin main
git checkout -b feat/dev-a-cts-skew
git branch --show-current

分支命名规范

核心要求：前缀 + 你的用户名 + 短描述，三段用 - 连。这样在 GitHub PR 列表里一眼能看出「谁在做什么」。

前缀用途示例（用户 dev-a）
feat/新功能feat/dev-a-cts-skew
fix/修 bugfix/dev-a-router-traversal
docs/文档docs/dev-a-onboarding
refactor/重构refactor/dev-a-state-machine
chore/琐事 / 配置chore/dev-a-gitignore

4️⃣ 改动代码 & 提交（让 AI 操作）

这是本流程最常被使用的部分。推荐做法：你专注「改对代码」，把繁琐的 git 操作交给 Claude Code。 AI 会主动检查 git status / git diff、起一个规范的 commit message、把命令打出来供你审核，再帮你执行。

典型对话

👤 你 我刚改完 router.py 加了一段路径校验，防止 skill 文件名做路径穿越。帮我提交一下。
🤖 Claude Code 好的，先看一下当前改动 … 
$ git status
$ git diff plugins/chip-backend-ai/core/router.py
我看到只改了 router.py 里的 _safe_path()。建议 commit message：
fix(router): validate skill filename to prevent path traversal
要这样提交吗？
👤 你 可以，提交吧。
🤖 Claude Code ✅ 已提交： 
$ git add plugins/chip-backend-ai/core/router.py
$ git commit -m "fix(router): validate skill filename to prevent path traversal"
当前分支 feat/dev-a-router-fix，共 1 个新提交。

你能这样自然地说

  • 「把我刚才所有改动提交一下，消息你看着写」
  • 「只提交 docs/ 下的文件，先别动 plugins/」
  • 「这次改了两件事，能拆成两个 commit 吗？」
  • 「我想看一下没提交的改动」（AI 会跑 git status + git diff）
  • 「刚才那个 commit message 不太对，帮我改成 …」（只要还没 push，AI 会用 --amend 修；push 了的话再开新 commit）

AI 会代你遵守的规则

  • 会先跑 git status / git diff，确认改了什么再写 message
  • 会按文件名 git add，不会盲目 git add -A 把敏感文件带进去
  • 会按 Conventional Commit 风格起 message：feat: … / fix: … / docs: …
  • commit message 第一行控制在 ≤ 70 字符，主要说为什么，不只是「做了什么」
  • 对已 push 的 commit 不会 用 --amend，避免污染别人的仓库
⚠️ AI 也会请你确认
碰到「删文件」「git reset --hard」「--force」这类有破坏性的操作， Claude Code 会先停下来问你。看到提示仔细读一遍再点同意。

5️⃣ 推送 & 发起 PR（让 AI 操作）

提交完，让 Claude Code 一气呵成把推送和 PR 都帮你搞定。

一句话发 PR

👤 你（dev-a） 把当前分支推到远端，然后帮我创建 PR，请 mentor 帮忙 review。
🤖 Claude Code 好的。当前分支 feat/dev-a-router-fix，还没有 upstream，我用 -u 建立追踪： 
$ git push -u origin feat/dev-a-router-fix
推送完成 ✓。
接着我看了一下这条分支与 main 的全部差异，准备 PR 描述： 
$ gh pr create \
    --title "fix(router): validate skill filename to prevent path traversal" \
    --body  "<Summary + Test plan>"
✅ PR 已创建：https://github.com/jasonsue687/chip-backend-ai/pull/123
需要我帮你 @mention reviewer 吗？

之后的协作循环

💬 回应 Review 意见
告诉 AI：「把刚才的改动追加上，然后 push」。 它会自动 git add + commit + push，PR 会自动同步。
🧹 合并后清理本地
PR 合并完，告诉 AI：「main 同步一下，把已经合掉的分支删掉」。 它会 checkout main → pull → branch -d。

常用句式

  • 「把当前分支 push 上去」（首次会自动加 -u）
  • 「开一个 PR，标题 …，描述 …，base 是 main」
  • 「看一下 CI 是不是过了」（AI 会跑 gh pr checks）
  • 「review 通过了，把这个 PR 合掉」（如果你有权限）
  • 「PR 合并后，清理一下我的本地分支」
⛔ AI 绝不会替你做的事
  • 直接往 main 推（即使你这么要求，它会先警告）
  • --force push 到主分支
  • 跳过 pre-commit hook（--no-verify）
  • 未经确认就删本地或远端分支
想自己用命令行做？点开看 
# 首次推送
git push -u origin feat/dev-a-router-fix

# 后续推送
git push

# 用 gh CLI 创建 PR
gh pr create --title "fix(router): ..." --body "..."

# 合并后清理
git checkout main
git pull origin main
git branch -d feat/dev-a-router-fix
git push origin --delete feat/dev-a-router-fix

6️⃣ 同步远端最新代码

开发过程中，别人会不断把改动 merge 到 main。你要定期把这些改动同步到自己分支，避免 PR 时出现大段冲突。

👤 你 把 main 最新的改动 merge 到我当前分支上。
🤖 Claude Code 好的，我先拉远端，再 merge 到 feat/dev-a-router-fix： 
$ git fetch origin
$ git merge origin/main
✅ Fast-forward 合并完成，没有冲突。
（如果有冲突，我会停下来列出冲突文件，等你决定怎么合。）

如果你想自己跑命令，两种方案都行：

# 站在你的开发分支上
git fetch origin
git merge origin/main

# 如果有冲突，编辑冲突文件后
git add <resolved files>
git commit              # 用默认 merge message

优点：操作简单，历史完整保留；缺点：会多出 merge commit。

git fetch origin
git rebase origin/main

# 冲突解决后
git add <resolved files>
git rebase --continue

# 已经 push 过的分支需要 force-with-lease 推
git push --force-with-lease

优点：历史线性、好读；缺点：已 push 后必须 force push，需要协作伙伴理解。

⛔ 永远不要在 main 上 rebase 或 force push

处理冲突的小贴士

  • 冲突文件里 Git 会插入 <<<<<<< HEAD / ======= / >>>>>>> 标记
  • 选择保留哪边、或两边都要的合并结果，删掉所有标记
  • 用 git status 看还有哪些 unmerged paths
  • 不确定的话找冲突双方的作者一起决定，不要凭感觉合

📋 Git 命令速查表

场景命令
查看状态git status
查看改动git diff / git diff --staged
查看日志git log --oneline --graph --all -20
查看当前分支git branch --show-current
列出所有分支git branch -a
切换分支git checkout <branch>
新建并切换分支git checkout -b <branch>
撤销工作区改动git restore <file>
撤销 add（保留改动）git restore --staged <file>
暂存当前改动git stash / git stash pop
拉远端但不合并git fetch origin
拉并合并git pull origin main
推送当前分支git push（首次加 -u origin <branch>）

查看某次提交git show <sha>

🚫 危险操作清单（用之前先问一句）
git reset --hard、git push --force、git clean -fd、 git branch -D——它们会不可逆地丢数据。除非你 100% 清楚后果，否则先和团队确认。

❓ 常见问题

Q1. 我应该把仓库 clone 到哪里？

团队约定：/path/to/<your-username>/chip-backend-ai/。 例如用户 dev-a 就放在 /path/to/chipcockpit/。 路径里不要出现中文或空格。

Q2. Claude Code 的 plugin 怎么指向我的本地仓库？

在 Claude Code 会话里说「帮我把这个本地路径注册成 plugin」， 或直接用 /plugin 命令，注册到 plugins/chip-backend-ai/ 这一层 （那一层有 .claude-plugin/plugin.json）。

完整路径示例（用户 dev-a）：

/path/to/chipcockpit/plugins/chip-backend-ai/

注册后，本地文件的任何修改都会被 Claude Code 立即看到（Python 改动需要 reload 一下）。

Q2.1 「插件开发」和「项目开发」是怎么连起来的？

就是通过上面这条路径：本地 git 仓库 → Claude Code plugin 注册 → 你的项目开发会话能用上你最新版本。 换句话说，你 push 到 GitHub 之前，只有你自己能用上这些改动；同事 git pull 拉到他自己的本地目录后， 他的 Claude Code 才会看到。

Q3. 不小心在 main 上提交了怎么办？

没 push 的话：

git branch feat/your-fix       # 给当前 commit 打分支标签
git reset --hard origin/main  # 把 main 拉回远端版本
git checkout feat/your-fix
git push -u origin feat/your-fix

已经 push 了：立刻找团队 maintainer，不要自己 force push。

Q4. 我的 PR 卡了很久没人 review？

① 在 PR 上 @ 指定 reviewer；② 群里友好催一下； ③ 确认 CI 通过、描述清晰。Reviewer 也是人，主动沟通永远比沉默有用。

Q5. 我能直接修改别人的分支吗？

原则上不要。除非对方明确请求你帮忙，并且你们约好了 push 节奏。 否则用 PR Review 留 comment / suggestion 是更礼貌的方式。

Q6. .gitignore 里我能加自己的私人文件吗？

请用全局 gitignore放个人偏好（如 IDE 配置）：

git config --global core.excludesfile ~/.gitignore_global

仓库的 .gitignore 只放所有人都应该忽略的内容（生成物、依赖目录等）。

Q7. 提交时被 pre-commit hook 挡了怎么办？

认真读报错信息，修好对应问题再 commit。不要用 --no-verify 跳过， hook 拦的就是不该入库的内容。

Q8. 想试一些会改 git 历史的操作，又怕搞坏？

把当前分支用 git branch backup-xxx 备一份，再操作。 出问题就 git reset --hard backup-xxx 回滚。
