AI 后端设计流程 · 架构与节点开发指引

顶部 Spec 层（Phase 0）把一份总需求（PPA 目标 / 自然语言）经 AI 分析扇出成各 stage 的约束并向下映射；其下横向 = 9 个 stage，纵向 = 每个 stage 的节点（标注该节点的 AI 决策点 / 输入 / 输出）。本图是流程架构设计， 用于指导同事按节点开发各步的 AI 能力（判断由决策 playbook skill 承接、主 agent 执行，无 sub-agent）。横切的执行/解析能力（run-eda-script、render-tcl、parse-eda-report）单列在「共享能力」页，不在节点上逐个重复。

Spec 层 — Phase 0：人类需求 → 规格 → 喂给每个 stage

芯片后端从一份人类主导的需求输入（PPA 目标 + 约束）开始：先结构化成 global_spec.yaml， 再把全局 PPA 预算分解到每个 stage（spec/stages/<stage>.yaml），人类审批后进入流水线。 之后每个 stage 开始时读取它那份 spec，作为只读的"北极星"喂给三类节点。spec 层属于状态机，坐在 flow_definition.yaml 之上。

Phase 0 流程（在流水线之前；编排器驱动、状态机记账）

机器级 bootstrap（流程之外·一次性）：env_manager detect/check 定位 Innovus —— 不 gate spec，resume 廉价校验
══════
INIT ─human_input─▶ SPEC_DRAFTING ─spec_ready─▶ SPEC_REVIEW ─human_approved─▶ SCHEDULING ─▶ STAGE_RUNNING
 人工：写 PPA       AI 决策 (spec-draft playbook)：      人工审批                         (flow_definition.yaml 接管)
 目标 + 约束        结构化 global_spec + 派生 per-stage spec
                                     ◀── human_rejected / revise_spec ──（驳回，或目标不可达时回炉）

"前置就绪"拆两半、各归其位（不再是顶部一道胖闸）：① env/工具 = 机器级一次性 bootstrap（env_manager，不 gate spec，resume 廉价校验即可）→ 归底部基座带 env 卡；② 输入齐全 + 版本一致 = 数据准备 → 归 import 头部（flow_loader blocked_inputs 查存在 ＋ 1 个 version-check skill 步查版本）。原因详见「共享能力」页的取舍说明。

① 人类需求输入 → global_spec.yaml（PPA 目标）

human_goal: "..."            # 人类原始意图（原文保留）
target_ppa:
  timing: { wns_ns: -0.1, tns_ns: -1.0, hold_wns_ns: 0.0 }
  power:  { total_power_mw: null }
  area:   { utilization_min: 0.60, utilization_max: 0.80 }
global_constraints: { technology: "tsmc_n5", design_intent: "..." }

② 预算分解：global → 每个 stage 的要求（AI 决策 + 人工确认）

全局 PPA 不能直接套用，要把它"分预算"给各 stage —— 这本身是判断，故由 spec-draft 决策、人类确认：

全局目标分解进 stage spec（节选）
area util 0.60~0.80floorplan：utilization 目标 ~0.70 · channel ≥ X
timing wns ≤ -0.1nscts：skew/insertion 目标 · route：timing 目标 · timing_eco：收敛余量
power 上限powerplan：IR/EM 预算 · placement/cts：功耗档位
两点务必把握（决定 spec 该怎么用）：① 这些 stage spec 是 AI 预测、可重预算的"收敛检查点"，不是 PPA 的硬切分合约——PPA 全流程涌现 + 强耦合，过紧的早期 gate 会造成假失败。② 只分解 PPA 预算型约束（timing/area/power，看板里紫框卡）；PDK/方法学固定型约束（DRC/EM/density/corner，灰框卡）一律加载、不由 AI 生成。

两级 spec：Phase 0 初版（粗）→ 进 stage 时细化（细）

Phase 0 信息最少，派生出来的只是初版 / 粗预算。真正喂给某 stage 的 spec，是在该 stage 进场时 just-in-time 生成的：

本 stage 初版 spec（Phase 0）
      ＋ 上游已积累的真实信息（actual 指标 / 拥塞 / skew / 寄生 …）
      ＋ 人工补充输入（额外约束 / 偏好）
      ──spec-draft 细化──▶ 本 stage 最终 spec ──▶ 喂该 stage 三类节点

这就是"滚动细化 rolling-wave"：开局给粗计划当北极星，临到每个 stage 再用最新真实数据 + 人工把它那份 spec 调准 —— 也天然接住了你要的"每个 stage 都能让人再补输入"。注意它和 ④ 的区别：这是开跑前的前向细化，④ 是 gate 失败后的后向回炉，两者互补。

③ 每个 stage 怎么用它那份 spec（喂三类节点）

stage 开始 → 读 spec/stages/<stage>.yaml
   ├─ metrics[].target      ──▶ 自动校验：gate 比对 actual vs target     ✅ 已接 parse-eda-report
   ├─ parameters / 目标      ──▶ AI 决策：作为判断依据与约束（决策 skill / 主 agent 读）
   └─ 全局 technology/corner ──▶ 自动执行：模板渲染参数
一句话：spec 是从上往下喂的"北极星"，和流水里流动的 def/db 产物是两条线 —— 后者是设计状态，前者是"什么算达标"。

④ spec 不是写死的：反馈回炉

某 stage gate 长期不过、目标不可达 → 状态机 revise_spec → 回 SPEC_DRAFTING 调 spec（如放宽某 stage 预算）→ 重新审批 → 继续流水线。

现状：global_spec_template.yaml / stage_spec_template.yaml / 状态机 SPEC_DRAFTING→SPEC_REVIEW / spec_manager.py 均已就位，parse-eda-report 已按 stage spec 的 metrics 做 gate。待补：把"global→stage 预算分解"明确成 spec-draft 的一步。spec 模板措辞已对齐无-agent（决策 skill / 主 agent / 自动校验）。

节点架构 — 一个节点内部是怎么分层的

看板上每个节点不是单一动作，而是一条内部流水线。AI 的价值集中在 ① 决策 和 ⑤ 诊断； ② 渲染 / ③ 执行 / ④ 自动校验是确定性的横切共享能力——这就是为什么 run-eda-script 等不画在每个节点上，而是抽到这一层只出现一次。

节点开发指引 — 怎么为一个节点开发 AI 能力

按节点类型对照开发。AI 决策步是主要工作量；自动执行/质量门/人工只需很少配置。

AI 决策步 完整六步（如 floorplan / cts / route / eco）

  1. 写黄金模板 templates/tcl/<stage>/<step>.tcl.tmpl：固定骨架 + {{占位符}} + ### @inject: 定制片段注入点。
  2. 定决策契约：约定该 step 的 <step>_decisions.yaml 长什么样 —— params（要填的参数）/ fragments（AI 写的片段）/ rationale（理由，便于审计）。
  3. 实现决策逻辑（写进该步的决策 skill / playbook，主 agent 执行）：读 spec + 上游产出 + 上次 eval → 推理出 decisions。这是该节点真正的"AI"。
  4. 接知识库 + 护栏：决策查 read-expert-doc/read-eda-concept；写片段查 read-eda-lab-doc；AI 写的每条命令必须过 search-eda-command 校验存在（防幻觉）。
  5. 复用共享层执行：decisions + 模板 → render-tcl → run-eda-script → parse-eda-report。不要自己写执行/解析代码。
  6. 配 flow_definition.yaml：把该节点写成 gen → run → eval 三元组并声明 inputs/outputs；重跑时把上次 eval 作为 gen 的额外输入（诊断回路）。

自动执行 / 质量门 / 人工确认

类型开发什么
自动执行只需第 ①、⑤、⑥ 步里的"模板 + 接执行"：写一份模板，参数直接来自 spec（无需判断），再走 render-tcl → run-eda-script。
质量门无需写代码：在 stage spec 里声明该门的 metrics（名称 + target），节点执行者填 parse-eda-report 即可。指标提取不准时给该指标加 pattern: 覆盖。
人工确认只写 instruction（让人做什么）。流程到此 await_human 暂停，人工完成后 resolve-human 继续。

红线（所有节点共同遵守）

  • 执行永远用共享 run-eda-script，别为某步单独写执行代码（否则就是 N 份雷同代码）。
  • AI 写的 Tcl 命令必须过 search-eda-command 校验，约束在真实命令空间内 —— 防幻觉的关键。
  • 每个 AI 决策落成 decisions.yaml：可审计、人可改了 re-render、新会话可续跑。
  • stub 不造假：工具缺失时产占位让流程结构走通，但绝不伪造 PPA 数字，下游 gate 如实报 missing。

判断放哪 & 决策 skill 怎么切分

判断不交给独立 sub-agent，而是写成决策 playbook skill（"怎么判断"的手册），由主 agent加载执行 —— skill 装方法 / rubric，运行时主 agent 对这颗芯片的真实数字现场推理，产出 decisions.yaml。skill 不装"结果"（每颗芯片都不同）。

切分判据：默认 1 个 stage 1 个 skill；满足任一条就把该 step 单拎成独立 skill：

  1. 它自身决策 / 知识量大，一个 playbook 写下去又长又散焦；
  2. 它有独立的诊断 / 迭代回路（如 drc_repair、fix_strategy）；
  3. 它会被单独复用（人工或别的流程直接调它）；
  4. 它和同 stage 其他步知识体系不同，硬合并会四不像。

反之：步骤短、共享同一套知识、总是一起做 → 合在一个 stage skill 里。务实做法：先按 stage 起步，写胖了 / 要独立复用了再拆；floorplan、route 已知较重，可一上来就按下表拆好。

取舍：为什么没有独立的"前置就绪"闸 / 胖 readiness-check skill？ 早先想把 工具 ＋ 输入齐全 ＋ 版本一致 合成一个横跨三者的胖 readiness-check 放流程最前、且"每次会话都重跑"。复盘后拆开各归其位 —— 因为三块的作用域和生命周期都不同：
① env / 工具：机器级、跨所有项目共享、存在 workspace 之外（env.json）—— 既塞不进 flow_loader 的输入模型（它只认 workspace 文件），也不该塞进 import（否则每个新项目都重找工具）。故它是机器 bootstrap，不 gate spec（spec 不调工具），resume 只 check 廉价校验。
② 输入齐全：flow_loader 的 blocked_inputs 逐文件查存在本就免费做了，跑到 import 自然拦。
③ 版本一致：一个确定性 version-check skill 步，放 import 头部。
结论：三块都有现成的家，不必再造一个胖闸。"每次会话都重跑"也被收回 —— 只对 env 的廉价 check 成立；②③ 是普通 flow 步、跑一次即 done，resume 不重跑。
