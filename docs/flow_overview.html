这套系统在做什么

一个高自治的芯片后端设计 AI 控制系统：把人类的模糊目标（如"跑通这个 block 的 route，congestion 别爆，时序稍微超一点没关系"）拆成可度量的 Spec，由编排器调度 Sub-agent 跑完 Floorplan → CTS → Route，遇到问题自己重试/回滚/改 Spec，关键节点要人审批。

三条核心设计选择

① 编排器是唯一决策中枢，Sub-agent 只干活不调度
② 所有交接走文件系统，禁止内存传海量上下文
③ Spec 是宪法，落盘前必须人类审批

谁在干活

Orchestrator 读状态/选路由/记日志
Spec Agent 意图 → YAML 契约
Floorplan / CTS / Route 三大主阶段
Timing ECO 按需修时序/DRC
Human 审批 Spec、做最终拍板

怎么知道结束了

COMPLETED 所有阶段 eval pass，命中 spec 中的 termination_criteria
ABORTED 全局重试预算耗尽 / 不可恢复错误

端到端闭环（点 Phase 展开）

编排器（skills/run-chip-flow/SKILL.md）按 Phase 0 → F 顺序推进。每个 Phase 都对应一条或多条 CLI 命令 + 一次状态机转移。

Phase 0环境准备 · 找到 Innovus›

每台机器一次性配置。配置存在 ~/.chip-backend-ai/env.json，跨项目共享。

# 检查 (退出码: 0=ok, 1=路径失效, 2=未配置)
python3 ${CLAUDE_PLUGIN_ROOT}/core/env/env_manager.py check --tool innovus

# 自动探测 (PATH / 环境变量 / 常见安装路径)
python3 ${CLAUDE_PLUGIN_ROOT}/core/env/env_manager.py detect --save

# 手动设置
python3 ${CLAUDE_PLUGIN_ROOT}/core/env/env_manager.py set --tool innovus --path /opt/cadence/INNOVUS221/bin/innovus

resume 时会再跑一次 check —— Innovus 可能已经被升级/搬路径。

Phase A工作区初始化 · INIT›

默认在当前目录下创建隐藏目录 ./.chipflow/（已存在则 .chipflow_2 自增）。不要让用户挑路径，除非他明确要求。

# 默认（推荐）
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py init

# 自定义路径
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py init --path <parent> --name <custom>
Phase BSpec 生成 · INIT → SPEC_DRAFTING → SPEC_REVIEW›

关键的人类协作点。未审批通过的 Spec 不允许后续任何 Sub-agent 工作。

  1. 向用户索取模糊目标 → 转移 human_input
  2. Agent 调用：chip-backend-ai:spec-agent，scenario=initial
  3. Spec Agent 写出 spec/global_spec.yaml 和 spec/stages/*.yaml
  4. 转移 spec_ready，把 spec 内容呈现给用户
  5. 人类批准 → human_approved + 写 spec_version=v1
  6. 人类拒绝 → human_rejected，带反馈再唤醒 Spec Agent，scenario=adjustment
Phase C调度循环 · SCHEDULING›

编排器的核心思考循环。每轮做三件事：读最新 eval_result、按决策树选 action、写一条 decisions.jsonl。详细决策逻辑见 编排器决策 一栏。

# 每轮三连
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py read --workspace <ws>
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py check-budget --workspace <ws>
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/decision_logger.py log --workspace <ws> ...
Phase D阶段执行 · SCHEDULING → STAGE_RUNNING›

创建 run 目录 → 转移 dispatch → Agent 调用 → 读 eval_result.yaml → 转移 agent_done → 回 Phase C。

python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/workspace.py create-run --workspace <ws> --stage floorplan
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py transition --workspace <ws> --event dispatch --detail "..."

Agent({
  subagent_type: "chip-backend-ai:floorplan-agent:Floorplan Agent",
  prompt: "Workspace: ...\nRun directory: ...\nSpec version: ...\nStage spec: ..."
})

# 回收：
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py update-stage --workspace <ws> \
  --stage floorplan --status passed --run-id run_001 --eval-path stages/floorplan/run_001/eval_result.yaml
python3 ${CLAUDE_PLUGIN_ROOT}/core/workflow/state_manager.py transition --workspace <ws> --event agent_done --detail "..."

⚠ 当前 CTS/Route/Timing ECO 仍是模拟模式，eval_result.yaml 里会带 simulated: true —— 务必在汇报时明示用户，不要拿假数据当真 PPA。

Phase ESpec 修订 · SCHEDULING → SPEC_DRAFTING›

同一阶段反复失败、约束看起来真的不可达时触发。流程和 Phase B 类似，区别是给 Spec Agent 喂 scenario=revision + 失败 eval 数据。

  • 修订后旧 Spec 进入 spec/history/global_spec_vN.yaml，spec_version 递增
  • 新 Spec 仍要走一次人类审批
  • 已完成阶段的 eval 是否被新 Spec "翻盘" 由编排器重新判断
Phase F收尾 · COMPLETED / ABORTED›
终态说明需要汇报给用户什么
COMPLETED所有阶段通过，命中 termination_criteria各阶段 PPA 摘要、workspace 路径、可交付 artifact 列表
ABORTED重试预算耗尽或不可恢复错误失败原因、预算消耗情况、最后一次 eval、可能的人工干预建议

工作区目录结构

每次启动新任务创建一个隔离的 workspace。只增不删：Spec 主文件可覆写但旧版本归档到 history/；run 目录永不回收。

workspace/ ├── spec/ │ ├── global_spec.yaml # 当前生效的全局 Spec │ ├── stages/ │ │ ├── floorplan.yaml # floorplan 阶段约束 │ │ ├── cts.yaml │ │ └── route.yaml │ └── history/ # Spec 变更历史（append-only） │ ├── global_spec_v1.yaml │ └── global_spec_v2.yaml │ ├── state/ │ ├── machine.yaml # 全局状态机快照（编排器读写） │ └── decisions.jsonl # 决策日志（append-only） │ ├── stages/ │ ├── floorplan/ │ │ ├── run_001/ │ │ │ ├── _meta.yaml # run 元数据 → 编排器索引入口 │ │ │ ├── eval_result.yaml # 自评估结果（带原始数值） │ │ │ ├── artifacts/ # Tcl / 约束文件 │ │ │ └── reports/ # EDA 原始 report │ │ └── run_002/ # 重试新 run，旧 run 不动 │ ├── cts/ │ │ └── run_001/ │ └── route/ │ └── run_001/ │ └── checkpoints/ # DEF/DB 快照（回滚恢复点） ├── post_floorplan_run001.def └── post_cts_run001.def

三份 YAML 契约

Sub-agent 和编排器之间只通过这三类文件通信。模板在 plugins/chip-backend-ai/templates/ —— 改字段先改模板，不要在协议外手搓字段。

① _meta.yaml · run 元数据

agent: floorplan_agent
stage: floorplan
run_id: run_001
timestamp: "2026-04-12T14:30:00Z"
spec_version: v2
parent_run: null          # 回滚后重跑指向触发 run
status: completed         # running | completed | failed
checkpoint: checkpoints/post_floorplan_run001.def

② eval_result.yaml · 自评估

stage: floorplan
run_id: run_001
spec_version: v2
overall: pass             # pass | fail | partial

metrics:
  - name: utilization
    target: { min: 0.65, max: 0.75 }
    actual: 0.71
    status: pass

recommendation: proceed   # proceed | retry | rollback | escalate
retry_context: null
escalation_reason: null

③ decisions.jsonl · 编排器决策日志（append-only）

{"ts":"2026-04-12T14:35:00Z","from":"SCHEDULING","to":"STAGE_RUNNING","action":"dispatch","target":"floorplan_agent","run_id":"run_001","reason":"Initial floorplan execution per spec v1"}
{"ts":"2026-04-12T15:10:00Z","from":"SCHEDULING","to":"STAGE_RUNNING","action":"retry","target":"floorplan_agent","run_id":"run_002","reason":"run_001 congestion 0.91 > threshold 0.85"}
{"ts":"2026-04-12T15:45:00Z","from":"SCHEDULING","to":"SPEC_DRAFTING","action":"revise_spec","reason":"floorplan run_002 still failing, utilization target may be too aggressive"}

协议红线

  • metrics 必含 target + actual，禁止只输出 pass/fail —— 编排器要能独立复核，Spec 改动后还要能"翻盘"老 eval。
  • Sub-agent 只评估本阶段。"floorplan 摆放是否导致 routing 拥塞" 这类跨阶段归因，编排器干。
  • Sub-agent 不写 state/machine.yaml。状态机只能由编排器经 state_manager.transition() 写。
  • run 目录永远不删。重试就 run_002/，回滚也保留触发 run 作为审计链。

编排器在 SCHEDULING 时怎么选下一步

每轮 SCHEDULING 的核心是读最新一份 eval_result.yaml + 当前阶段重试预算 + 全局预算，套下面这棵决策树。

读 state/machine.yaml （当前状态全貌） 读 最近一次 run 的 eval_result.yaml ┌─ IF 还没跑过任何阶段（全部 pending） │ → dispatch 第一个阶段（floorplan） │ ├─ IF eval.overall == pass │ ├─ 满足 termination_criteria → all_passed → COMPLETED │ └─ 否则 → dispatch 下一个 pending 阶段 │ ├─ IF eval.overall == fail │ ├─ 阶段 retry_count < max_stage_retries → retry 同阶段（run+1） │ ├─ eval.recommendation == rollback → dispatch 更早阶段，parent_run 指向当前失败 run │ ├─ 全局预算耗尽 → budget_exhausted → ABORTED │ └─ 否则 → revise_spec（派 Spec Agent，等人重审） │ └─ IF eval.overall == partial ├─ 失败指标不阻塞下游 → proceed └─ 阻塞 → 按 fail 分支处理

跨阶段回滚怎么走

  1. 识别哪个上游阶段的产物可能造成下游失败（编排器跨阶段归因，Sub-agent 不参与）。
  2. 从 checkpoints/ 加载对应的上游 checkpoint。
  3. 在上游阶段创建新 run，parent_run 指向当前失败 run（保留审计链）。
  4. 全局重试预算 +1。

失败注入（用于离线调试编排逻辑）

EDA 没接入前，所有阶段 agent 默认走通过路径。要测试 retry / rollback / revise_spec / abort 分支时，在用户提示中触发失败计划，编排器在 dispatch prompt 里附加：

Simulate fail: true
Fail metrics: clock_skew, max_transition       # 可选，省略则全部失败
Recommendation: retry|rollback|escalate|proceed
Escalation reason: <text>                      # 仅 escalate 时

⚠ 注入失败时必须明确告知用户："[sim] CTS run_001 将被人为标记失败, recommendation=retry"，避免和真 PPA 混淆。
