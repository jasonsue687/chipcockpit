后端流程 YAML 化 · 3 方案三选一

当前 chip-backend-ai 的"后端开发流程"散落在 5 处（state_manager.TRANSITIONS、workspace.DEFAULT_STAGES、global_spec_template.stages、run-chip-flow SKILL 的散文决策树、5 个 AGENT.md）。 目标是用一份 flow.yaml 作为流程的唯一定义。每个阶段除了声明执行者，还显式声明 inputs / outputs，让流程同时是数据流契约。

flow.yaml  · 插件内 1 份，所有项目共用

定义结构 + 数据流：阶段顺序、每阶段用哪个 subagent/skill、读哪些文件、写哪些文件、失败做什么。 结构基本不变，所以共享。本次比选的就是这份文件的形态。

global_spec.yaml  · 每个 workspace 1 份（已存在）

定义参数：utilization 区间、congestion 阈值、retry 预算具体数值、PPA 目标。 这些每个项目都不一样，本来就是 per-workspace 的，不在本次讨论范围。

每个 stage 的契约：executor + inputs + outputs

flow.yaml 中每个 stage 都声明"用什么执行（subagent 或 skill）、读哪些文件、产出哪些文件"。 编排器在 dispatch 前能校验输入就绪，把解析后的具体路径注入 sub-agent prompt； sub-agent 自身不需要硬编码任何路径，跨阶段数据依赖（如 CTS 用 Floorplan 产出的 checkpoint）由 {stages.X.outputs.Y} 显式引用。

{ws} = workspace 根路径 {run_id} = 当次 run（dispatch 时解析为 run_001 等） {stages.X.outputs.Y} = 跨 stage 引用上游声明的输出 executor.type = subagent | skill

3 个方案详细对比

方案 A · 增强 Stage List

最小改动 · 务实推进 · 线性管道 + 显式 I/O 契约
# plugins/chip-backend-ai/flows/flow.yaml （新增 · 插件内 1 份）
flow:
  name: standard_backend_flow
  version: 1
  stages:
    - id: floorplan
      executor: { type: subagent, name: floorplan-agent }
      inputs:
        - "{ws}/spec/global_spec.yaml"
        - "{ws}/spec/stages/floorplan.yaml"
      outputs:
        meta:       "{ws}/stages/floorplan/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/floorplan/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_floorplan_{run_id}.def"
        artifacts:  "{ws}/stages/floorplan/{run_id}/artifacts/"
      on_fail: revise_spec
      rollback_to: null

    - id: cts
      executor: { type: subagent, name: cts-agent }
      inputs:
        - "{ws}/spec/stages/cts.yaml"
        - "{stages.floorplan.outputs.checkpoint}"     # 数据依赖
      outputs:
        meta:       "{ws}/stages/cts/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/cts/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_cts_{run_id}.def"
      on_fail: rollback
      rollback_to: floorplan

    - id: route
      executor: { type: subagent, name: route-agent }
      inputs:
        - "{ws}/spec/stages/route.yaml"
        - "{stages.cts.outputs.checkpoint}"
      outputs:
        meta:       "{ws}/stages/route/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/route/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_route_{run_id}.def"
      on_fail: rollback
      rollback_to: cts

  on_demand:
    - id: timing_eco
      executor: { type: subagent, name: timing-eco-agent }
      inputs:
        - "{stages.last_passed.outputs.checkpoint}"   # 当前最后一个 pass
      outputs:
        meta:       "{ws}/stages/timing_eco/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/timing_eco/{run_id}/eval_result.yaml"
      trigger: orchestrator

  termination:
    all_stages_passed: true
    timing_signoff: true

  • Sub-agent 不再硬编码路径，由编排器注入
  • 不破现有心智模型，最容易迁移

  • 状态机仍硬编码在 Python
  • 未来加多 corner 要再改架构

方案 B · DAG 工作流

中等改动 · 工业可扩展 · 数据流即依赖图
# plugins/chip-backend-ai/flows/flow.yaml （新增 · 插件内 1 份）
flow:
  name: standard_backend_flow
  version: 1
  nodes:
    floorplan:
      executor: { type: subagent, name: floorplan-agent }
      inputs:
        - "{ws}/spec/stages/floorplan.yaml"
      outputs:
        meta:       "{ws}/stages/floorplan/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/floorplan/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_floorplan_{run_id}.def"
      on_fail: { action: revise_spec }

    cts:
      executor: { type: subagent, name: cts-agent }
      inputs:
        - "{ws}/spec/stages/cts.yaml"
        - "{nodes.floorplan.outputs.checkpoint}"      # 依赖 = 数据依赖
      outputs:
        meta:       "{ws}/stages/cts/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/cts/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_cts_{run_id}.def"
      on_fail: { action: rollback, target: floorplan }

    route:
      executor: { type: subagent, name: route-agent }
      inputs:
        - "{ws}/spec/stages/route.yaml"
        - "{nodes.cts.outputs.checkpoint}"
      outputs:
        meta:       "{ws}/stages/route/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/route/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_route_{run_id}.def"
      on_fail: { action: rollback, target: cts }

    timing_eco:
      executor: { type: subagent, name: timing-eco-agent }
      inputs:
        - "{nodes.route.outputs.checkpoint}"
      outputs:
        meta:       "{ws}/stages/timing_eco/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/timing_eco/{run_id}/eval_result.yaml"
      when: "metrics.timing.wns_ns < -0.1"           # 条件触发

  termination:
    when: "nodes(['floorplan','cts','route']).all_passed"

方案 C · 完整状态机 YAML

最大改动 · 最显式 · 状态机 + I/O 契约一并搬进 YAML
# plugins/chip-backend-ai/flows/flow.yaml （新增 · 插件内 1 份）
flow:
  name: standard_backend_flow
  initial: INIT
  states:
    INIT:
      on: { human_input: SPEC_DRAFTING }
    SPEC_DRAFTING:
      entry: spawn(spec-agent)
      on: { spec_ready: SPEC_REVIEW }
    SPEC_REVIEW:
      on:
        human_approved: SCHEDULING
        human_rejected: SPEC_DRAFTING
    SCHEDULING:
      entry: decide_next
      decisions:
        - when: "all_stages.status == 'passed'"
          to: COMPLETED
        - when: "budget.exhausted"
          to: ABORTED
        - when: "last_eval.overall == 'fail' and stage.retry < budget.max"
          to: STAGE_RUNNING
          action: retry
    STAGE_RUNNING:
      entry: spawn(${current_stage.executor})
      on: { agent_done: SCHEDULING }
    COMPLETED: { final: true }
    ABORTED: { final: true }

  stages:
    - id: floorplan
      executor: { type: subagent, name: floorplan-agent }
      deps: []
      inputs:
        - "{ws}/spec/stages/floorplan.yaml"
      outputs:
        meta:       "{ws}/stages/floorplan/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/floorplan/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_floorplan_{run_id}.def"

    - id: cts
      executor: { type: subagent, name: cts-agent }
      deps: [floorplan]
      inputs:
        - "{ws}/spec/stages/cts.yaml"
        - "{stages.floorplan.outputs.checkpoint}"
      outputs:
        meta:       "{ws}/stages/cts/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/cts/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_cts_{run_id}.def"

    - id: route
      executor: { type: subagent, name: route-agent }
      deps: [cts]
      inputs:
        - "{ws}/spec/stages/route.yaml"
        - "{stages.cts.outputs.checkpoint}"
      outputs:
        meta:       "{ws}/stages/route/{run_id}/_meta.yaml"
        eval:       "{ws}/stages/route/{run_id}/eval_result.yaml"
        checkpoint: "{ws}/checkpoints/post_route_{run_id}.def"

优点
  • 唯一真源 —— FSM + I/O 全部 YAML
  • 可直接生成状态图和数据流图
  • 未来加新状态无需动 Python
缺点
  • YAML 嵌套深，写起来啰嗦
  • DSL 表达式集需严格定义
  • 当前业务复杂度可能用不到这种灵活性
共性提示： 三个方案的 stage schema 完全一致 —— id / executor / inputs / outputs / on_fail。 区别只在顶层组织方式：A 用平坦 stage 数组，B 用 nodes 字典（依赖从 inputs 推导），C 在 stages 之外加上 states/transitions 块。
executor.type 当前两种：subagent（走 Agent 工具）与 skill（走 Skill 工具）。 当前 5 个领域 Agent 都是 subagent；未来想把某个轻量步骤换成 skill 实现，只改这个字段，编排器无感。
三个方案对 stage_simulator.py 完全兼容 —— I/O 契约只决定"路径怎么传给 agent"，不决定"agent 怎么跑"。
