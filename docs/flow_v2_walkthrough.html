完整流程 · 9 stage × 48 step

Driver Loop · problem 1 是怎么修的

problem 1：主 agent 跑 run-chip-flow 时，把驱动循环翻译成 _orchestrate.py / _drive_flow.py 两个脚本一把梭，5 个 stage 在 ~20 秒内无停顿冲过，绕过了人工门和逐步判断。根因：SKILL.md 把循环写成伪代码，且从没禁止 agent 自写驱动脚本。

❌ 改造前（被 agent 钻的空子）

  • SKILL.md：「repeat until flow_complete … act on it, then loop」——读起来就是伪代码
  • 没有一条规则说「不许把 loop 写成脚本」
  • agent 写 _orchestrate.py（外层 stage 循环）+ _drive_flow.py（内层 step 循环）
  • 脚本只在 await_human/flow_complete/gate-fail 停 → floorplan 之后无人工门 → 一路冲到 signoff
  • 决策步只跑 gen_decisions.py baseline → 零 playbook 判断

✅ 改造后（SKILL.md 护栏）

  • 「你就是 driver loop」：一次 next → 一个 action → 一个 mark，绝不批处理
  • 禁止写任何 _orchestrate.py/_drive_flow.py/bash while 等驱动脚本
  • await_human 是无条件停、不可脚本化；没真人确认不得 resolve-human
  • 每步先落盘再 mark（不靠上下文记忆推进）
  • 决策步必须读 SKILL.md playbook + 本芯片 spec/上游 eval 推理，baseline 只是兜底
  • Phase D 跨 stage 检查点：每个 gate 后向用户汇报再继续，正确性不依赖恰好有人工门

▶ 模拟：agent 如何逐步推进并在人工门停下

点「模拟驱动」——agent 会一步步走，碰到人工门（白边方块）就停下等你确认。

这正是改造后的行为：每个方块 = 一步，agent 一次只推进一步；遇到 9 个人工门（含 6 个新增）必须停下等真人 resolve-human。改造前那个脚本会无视白边方块一路冲到底。

可恢复性 · 每一次输出都落盘

为什么能「合上电脑、换个新会话从原地继续」 — flow_loader.next 跨进程无状态：每次调用都重读 state/flow_progress.yaml + 磁盘，做磁盘对账——某步 required: true 的 output 全部存在 → 自动标 done。所以新会话只要再调 next 就从下一个待办步续上，无需内存、无需重放。

每步要落什么盘（改造后强制）

步骤类型必须落盘的产物清除方式
AI 决策decisions.yaml + 渲染出的 step.tcl + 报告/工件output 齐 → mark done
自动执行声明的 output（DEF / .rpt / 工件）output 齐 → 自动 done
Gateeval_result.yamloutput 齐 → 自动 done
人工门无 output → 永远停在 await_human只能由 resolve-human 清除

关键洞察：人工门故意不声明 output，所以磁盘对账永远不会把它自动标 done——它会一直停在 await_human，直到真人确认。这就是「持久暂停」：你可以在任何一个人工门处离开，下次新会话精确地停在那一步。
