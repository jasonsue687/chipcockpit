LLM 驱动宏单元放置 · 架构方案

面向疑问 "LLM 处理坐标差、空间推理弱，能搞定 floorplan 吗？" 给出的明确架构答复 · 聚焦 Cadence Innovus，不涉及 SA / ILP / 自研求解器

一句话结论：本架构里 LLM 从头到尾不计算任何坐标。它只生成"约束 DSL"（意图层）， 几何由 Innovus 自带的 place_design 在受约束的可行域里求解。 LLM 弱在 2D 推理 —— 我们就不让它做 2D 推理。

1 · 核心疑问的复述

你提出的质疑非常具体，可以拆成四条独立论断。它们都部分正确，所以必须分别回应：

有人说：宏单元放置是 LLM 比较难搞的事情

  • 论断 A：这是带约束的二维布局优化问题，本质需要空间推理 + 多目标权衡（时序、拥塞、电源、面积）。
  • 论断 B：LLM 处理坐标的能力非常差，经常给出宏重叠、超出 die、违反对称的坐标。
  • 论断 C：即使用 chain-of-thought，LLM 也很难在脑子里维护一个二维网格状态。
  • 论断 D：这正是 Google 2021 Nature 论文用 RL 而不是 LLM 的原因。

我对这四条论断的判定

论断判定关键澄清
A · 这是 2D 约束优化 完全正确 事实陈述。但"问题是 2D 优化"不等于"必须由 2D 推理者求解" —— 几何求解可以交给专门工具。
B · LLM 给坐标会错 经验上正确 所以本架构里 LLM 不被要求输出坐标 —— 这条论断只能否定"naive 让 LLM 直出坐标"那一种方案。
C · CoT 维护不了 2D 状态 部分正确 Transformer 序列化注意力确实无原生空间状态；但状态可以放在外部（tool 调用），LLM 只做增量决策。
D · Google 用 RL 所以 LLM 不行 非充分论证 那篇论文 2020 年投稿，没有现代 LLM；且本身被 Cheng et al. 2023 质疑过可复现性。"当年 Google 没选 LLM" ≠ "今天 LLM 解决不了"。RL 与 LLM 不互斥 —— 成熟系统会让 LLM 做语义层、RL/算法做几何层。
关键洞察：批评打中的只是 "LLM 直接生成坐标" 这一种 naive 用法。 本架构的核心设计就是把 LLM 从几何层撤出来，让它只工作在意图层和约束层。

2 · 一句话答复（再展开三层）

本架构如何回避论断 B/C：

LLM 输出的是 结构化约束（DSL），比如 {group: bank0, topology: 4x4_array, pitch: [120,80]}、 {ctrl above bank0 by 30um}。
所有坐标计算由两类执行者完成：
  ① Python 适配器：规则性几何（如阵列循环 x = origin + i*pitch），这是死代码，不是优化；
  ② Innovus place_design：在约束划定的可行域内做真正的 2D 优化（wirelength、congestion、std cell legalization）。
LLM 全程没有写过任何坐标数字。

类比：你不会让 LLM 算 23 位乘法

LLM 算大数乘法会错得离谱，但没人因此说 "LLM 不能用于数学" —— 正确用法是让它调计算器或写 Python，而不是当计算器。floorplan 是一样的：

错误用法 naive

把 die 尺寸和宏列表丢给 LLM，让它直接输出 placeInstance bank_0 234 567 R0。

这种用法验证了论断 B/C —— 宏一多就重叠 / 出界 / 违反对称。

本方案 constraint-based

LLM 输出约束 DSL；适配器翻译成 Innovus TCL；Innovus 自己算坐标。

LLM 弱项被完全绕开 —— 它做擅长的语义翻译，几何交给擅长的求解器。

这是后续所有内容的总线索：无论看到 LLM 还是 Python 还是 TCL，时刻问一个问题 —— "这一步在算坐标吗？如果是，谁在算？" 答案永远不应该是 LLM。

3 · 三层架构（点击左侧层级查看职责）

从用户意图到 Innovus 最终 DEF，整个流水线被严格分成 4 层。关键不变量：越往上越接近"意思"，越往下越接近"几何"；LLM 只允许待在上面两层。

Layer 1 · INTENT
LLM（spec-agent + floorplan-agent）
理解人类意图 → 结构化约束
语义层
↓ 生成 YAML
Layer 2 · CONSTRAINT
macro_constraints.yaml（DSL）
可审计、可 diff、可回归的中间产物
协议层
↓ Python 适配器（死代码）
Layer 3 · TCL SETUP
innovus_adapter.py → setup.tcl
规则坐标 + 约束 API 调用 + place_design
绑定层
↓ Innovus 内置 placer
Layer 4 · GEOMETRY
Innovus place_design / refine_macro_place
真正的 2D 优化、wirelength、congestion
求解层

层级间的契约（contract）

边界契约形式检验方式
L1 → L2 YAML schema (templates/macro_constraints_template.yaml) jsonschema 校验；缺字段直接拒收
L2 → L3 Python 适配器函数签名（dataclass in, str out） 单元测试：固定 DSL → 固定 TCL diff
L3 → L4 Innovus TCL 命令集（标准 EDA API） Innovus 语法检查；place_design 报错即失败
L4 → 反馈 eval_result.yaml（congestion / violations / 截图） 对照 stage spec 的 acceptance criteria
切勿做的事：不要让 LLM 直接生成 Layer 3 的 TCL，更不要让它生成 placeInstance bank_0 234 567 这种带具体坐标的命令。 一旦 LLM 写出了坐标数字，本架构就退化成被论断 B/C 否定的 naive 方案。

5 · naive 方案 vs 本方案

同样让"LLM 帮忙做 floorplan"，下面两种架构的命运完全不同。

✗ naive：LLM 直接吐坐标

# LLM prompt:
# "die 800x600, 把 4 个 200x150 的
#  bank 排成 2x2, 不要重叠"

# LLM 输出:
placeInstance bank_0 100 100 R0
placeInstance bank_1 350 100 R0
placeInstance bank_2 100 320 R0
placeInstance bank_3 350 350 R0  ← 不对齐
#    ↑ 还可能重叠、出界、忘对称
  • 坐标由 LLM 凭"感觉"生成
  • 宏数量 > 20 急剧恶化
  • 无法表达"在 X 北边"这种相对约束
  • 无法利用 Innovus placer 的 wirelength 优化
  • congestion / timing 完全没考虑
  • 验证了论断 B / C

✓ 本方案：LLM 产约束，Innovus 算坐标

# LLM 输出（DSL）:
groups:
  - {name: dram, macros: [bank_0..3],
     topology: 2x2_array,
     pitch_um: [220,180], origin: [100,100]}
relative:
  - {a: ctrl, b: dram, relation: above,
     channel_um: 30}

# 适配器 → TCL:
placeInstance bank_0 100 100 R0 -fixed
placeInstance bank_1 320 100 R0 -fixed
placeInstance bank_2 100 280 R0 -fixed
placeInstance bank_3 320 280 R0 -fixed
createRegion ctrl_r 100 490 540 600
addToRegion ctrl_r ctrl
place_design -concurrent_macros  ← Innovus 干活
  • LLM 完全不写坐标 → 论断 B/C 不适用
  • 2×2 阵列坐标由 Python 循环加法算（非优化）
  • ctrl 位置由 Innovus 在 region 内挑最优
  • std cell legalization、wirelength 优化全部由 Innovus 完成
  • DSL 可 diff、可回归、可被人类审查
  • 退一步：即使 LLM 完全摆烂随机生成 DSL，Innovus 也会拒绝非法约束 —— 有 fail-fast

性能与可扩展性对比

维度naive本方案
宏数量上限≤ 10 凑合无明显上限（取决于 Innovus）
支持相对约束（"X 在 Y 北边"）不支持原生支持
支持对称 / 对齐 / abutment勉强（很容易破坏）via createRegion / placeInstance -fixed
wirelength 优化无Innovus placer 内建
congestion 反馈无place_design 后 report_congestion
可审计差（坐标黑盒）好（DSL 可 diff）
可回归难（LLM 输出不稳定）易（适配器是死代码）
失败模式静默错误（坐标看起来对，其实重叠）fail-fast（Innovus 报错）

6 · Innovus 约束 API · 适配器能用的"积木"

DSL 翻译的目的地，就是下面这些 Innovus 原生命令。LLM 不需要知道它们的语法 —— 适配器知道就行。

放置类

命令用途典型示例
placeInstance 把宏固定在精确坐标 placeInstance bank_0 100 100 R0 -fixed
place_design 触发 Innovus placer（含宏 + std cell） place_design -concurrent_macros
refine_macro_place place_design 后微调宏位置 refine_macro_place

区域类（可行域）

命令用途典型示例
createRegion 软约束：尽量在区域内 createRegion ctrl_r 100 490 540 600
createFence 硬约束：必须在区域内 createFence sym_r 0 0 400 600
addToRegion / addToFence 把实例绑定到区域 / 围栏 addToRegion ctrl_r ctrl
defineProximityGroup 声明一组实例应靠近 defineProximityGroup bank_grp -insts {bank_0 bank_1 …}

禁区与边距类

命令用途典型示例
createPlaceBlockage 禁止放置的多边形区域 createPlaceBlockage -box {50 50 150 150} -type hard
createPlaceHalo 宏周围的隔离带 createPlaceHalo -allMacros -halo 10 10 10 10
createRouteHalo 布线层面的 halo createRouteHalo -allMacros -space 5

引脚与边界类

命令用途典型示例
editPin 指定 IO pin 所在边 editPin -pin {io_*} -side bottom -spread
setObjFPlanBox 修改 die / core 框 setObjFPlanBox Module top 0 0 800 600

验证类（Innovus 给反馈给 LLM 用）

命令用途反馈给 LLM 的形式
check_floorplan 检查重叠 / 出界 / 非法约束 错误数 + 前 N 条具体违反
report_congestion 拥塞报告 + 热力图 峰值 H/V overflow + map 截图
report_timing -early pre-CTS 时序 WNS / TNS + top 5 violating path
设计原则：适配器只用"声明性"命令（createRegion / createFence / createPlaceHalo）， 避免"过程性"命令（一步步 moveInstance）。声明性命令 = 把决策权留给 Innovus 的优化器。

7 · 闭环修正（Layer 4 → Layer 1 的反馈）

这是第二个让 LLM 有用的关键 —— 当 Innovus 跑完 place_design 后报 congestion， LLM 不需要"看着 2D 网格在脑子里推理"，它只需要看一张压缩后的反馈摘要，然后修改 DSL 里的几个参数。

反馈包结构（eval_result.yaml 节选）

stage: floorplan
status: needs_revision
metrics:
  congestion:
    h_overflow_peak: 1.8   # > 1.0 即过拥塞
    v_overflow_peak: 0.9
    hotspot_region: {x: 320, y: 280, w: 100, h: 80}   # ← bank_3 周围
  timing_pre_cts:
    wns_ns: -0.42
    tns_ns: -3.1
  violations:
    overlap_count: 0
    out_of_die: 0
attachments:
  congestion_map: stages/floorplan/run_001/cong_map.png
  density_map: stages/floorplan/run_001/density.png
hints_for_llm:                # 适配器预先压缩好的关键事实
  - "Hotspot at bank_3 area; channel between bank_2 and bank_3 is 20um (too tight)"
  - "ctrl region narrowness causes long routes to bank_0"

LLM 在反馈循环里的"动作"是什么？

不是 ✗

不是让 LLM 看着 congestion map 在脑子里搬宏。LLM 看不准像素坐标。

而是 ✓

LLM 看 hints_for_llm 里的事实文本，决定修改 DSL 里的哪个参数： 例如把 channel 从 20um 改成 40um，或者把 ctrl 的 region 加宽。

典型修正动作（DSL 级别）

问题LLM 的修正结果
bank 间 channel 过窄 → routing 拥塞 把 pitch_um 从 [220,180] 改为 [240,200] 适配器重新算坐标，bank 间隙变大
ctrl 离 bank_0 太远 把 {ctrl above dram} 改成 {ctrl above bank_0 abutment} 适配器加 placeInstance ctrl -fixed
某 region 内 std cell 密度过高 在 DSL 加 blockage: {box: ..., type: partial, density: 0.5} 适配器加 createPlaceBlockage -density 0.5
循环的关键设计：每次迭代 LLM 改的都是 少量、命名清晰 的 DSL 参数 —— 这是它擅长的"局部语义编辑"，不是它弱势的"全局空间重规划"。

8 · FAQ

Q1 · 那 LLM 在这个方案里到底"聪明"在哪？

LLM 的价值在两个地方，都跟坐标无关：

  1. 把模糊人类需求翻译成结构化约束。 "排成阵列、留 channel、对称、和 PG 网络对齐" 这些半结构化的意图，传统脚本写不动，模板覆盖不全 —— LLM 在这里是最合适的工具。
  2. 在闭环里读反馈、做增量调整。 看到 "bank_3 周围拥塞、channel 20um" 这种文本事实，LLM 知道"应该把 pitch 加大" —— 这是常识级推理，不是空间几何推理。

它绝不算坐标、绝不维护 2D 状态、绝不和 Innovus 的 placer 抢活干。

Q2 · 如果用户直接说"把 bank_0 放在 (234, 567)"怎么办？

这是合法的 —— DSL 支持显式坐标： fixed_placement: [{inst: bank_0, x: 234, y: 567}] —— 适配器原样翻译成 placeInstance bank_0 234 567 R0 -fixed。是用户在算坐标，不是 LLM。 LLM 在这里只做"把自然语言识别成 fixed_placement 条目"这件小事。

Q3 · 如果 DSL 自相矛盾（如 ctrl 同时被要求在北边又在南边）怎么办？

三道防线：

  1. schema 校验：YAML schema 检查字段类型和必填项。
  2. 适配器语义检查：翻译前先做 cross-rule 检测（同一 instance 不能被两个矛盾的 relative 约束）。
  3. Innovus 兜底：check_floorplan 会报"区域内放不下" / "超出 die" 等错误。

任何一道失败，整个 stage 标记 failed，反馈 hints_for_llm，触发下一轮迭代。

Q4 · 这个方案的成本在哪？比 naive 多花了什么？

主要成本是一次性的：

  • 定义 DSL schema（一次）—— 估计 1~2 周设计 + 评审
  • 写 Innovus 适配器（一次）—— 估计 2~3 周，覆盖 DSL 所有原语
  • 积累反馈摘要模板（持续）—— 每次发现新的失败模式，加一条 hint 规则

之后 LLM prompt 和 sub-agent 只需指向 DSL，没有额外开销。边际成本几乎为零。

Q5 · 这套架构能扩展到 CTS / Routing 吗？

能，而且是同一个模式的复用：

  • CTS：LLM 产 clock_constraints.yaml（root buffer 位置约束、skew 目标、useful skew 提示），适配器翻译成 create_clock_tree_spec / ccopt_design。
  • Routing：LLM 产 routing_constraints.yaml（layer 偏好、屏蔽线、非默认规则），适配器翻译成 setNanoRouteMode + route_design。

同样的原则：LLM 不算几何，只产约束；EDA 工具内置算法做求解。

Q6 · 那 RL 还有用武之地吗？

有 —— 在更深一层：当某一类设计（如 DRAM bank 阵列）需要从大量历史 case 学一个泛化的 floorplan policy， 可以用 RL 在 DSL 层 自动生成约束，再走本架构剩余的 Layer 2 → 4。 也就是说：RL 可以替代 LLM 的 Layer 1，但仍然不直接产坐标，仍然要经过 DSL 和 Innovus。 LLM 和 RL 不是替代关系，而是 Layer 1 上的两种不同实现选项。

Q7 · 实际落地的最小可行版本是什么？

三件事可以并行：

  1. DSL 模板：templates/macro_constraints_template.yaml，先覆盖 groups / relative / edge_pins / halos / fixed_placement 五类
  2. Innovus 适配器骨架：core/workflow/macro_placer/innovus_adapter.py，把 DSL 翻成 TCL 字符串
  3. floorplan-agent prompt：在 agents/floorplan-agent/AGENT.md 加一段 "你的输出只能是 DSL YAML，不允许出现坐标数字"

跑一个 X1 DRAM 小 case 走通整条流水线就算 MVP 完成。
